# laya-apple v0.2 benchmark report — heterogeneous execution

**Scope.**
- `Laya(execution="workers")` serving MLX (GPU) and Core ML (ANE) concurrently, measured
  through the product API.
- A closed-loop exit-gate mix and open-loop mixed workloads.
- Correctness is checked on every request against the inline result for the same device.

Single-request latency is unchanged from v0.1 (`benchmarks/v0.1.md`).

## Setup

- **Hardware and software:** Apple M4 Max, macOS 26.6.2 (25G83), Python 3.12.14, MLX
  0.32.2, coremltools 9.0, laya-apple 0.2.0. The v0.1 artifacts built from the release
  commit are used.
- **Driver:** `scripts/bench_concurrency.py`. Tables are from `scripts/concurrency_report.py`.
  Raw windows with every latency sample are in `benchmarks/v0.2/*.json`.
- **Part A (exit gate):**
  - The Phase -1 mix: one short and one long stream, one question each, closed loop, one
    client thread per stream, all through one `Laya` instance.
  - Conditions: solo_short, solo_long, hetero (`device="auto"`), and gpu_only
    (`device="gpu"`, both streams on the one MLX queue).
  - 20 s windows, 3 cycles, alternating order. Medians over cycles.
  - Run once with the ANE on a thread in the caller's process, and once in a worker
    process. The GPU is always a worker process.
- **Part B (open loop):**
  - Poisson arrivals, plus a bursty variant (1 s at 3× the rate, then 2 s idle, with the
    same mean).
  - Request classes: 60% short 1-question, 20% medium 1-question, 10% long 1-question,
    10% short 4-question.
  - The same arrival sequence for `auto` and `gpu_only`. Latency runs from arrival to
    result, queueing included.
- **Placement choice:** `scripts/derive_placement.py` picks, per model, the ANE placement
  with the lower hetero short-stream P99 in Part A, and writes
  `laya_apple/data/placement.json`.

## Exit gate (revised)

| Criterion | laya | laya-multilingual | laya-typed-decisions |
|---|---|---|---|
| Aggregate ≥ 2.5× the best single device, vs product GPU-only | **pass** (2.93×) | **pass** (3.56×) | **pass** (4.61×) |
| Same criterion, vs the best GPU-only measured anywhere (MLX streams in separate processes: Phase -1 / step 1) | not measured | **fail** (2.15× of 92.3 req/s) | **pass** (3.21× of 34.4 req/s) |
| No answer change under load (all Part A and Part B requests) | **pass** (0) | **pass** (0) | **pass** (0) |
| Original: each stream's P99 within 10% of solo | short +5%, long +16%: **not met** | short +99%, long +21%: **not met** | short +8%, long +13%: **not met** |

Notes on the gate:
- **Why the P99 criterion was not met.** It was set from self-driven loops. For
  request-driven serving, none of the seven designs tested meets it on this platform
  (`research/v0.2-concurrency/`). The revised plan therefore reports isolation as measured
  and does not substitute a threshold chosen after the fact.
- **What isolation buys against the realistic alternative (Part B, short 1-question
  requests):**

  | Model | Workload | P99 with `auto` | P99 with GPU-only |
  |---|---|---:|---:|
  | laya | bursty, 46 req/s | 103 ms | 1548 ms |
  | laya-multilingual | Poisson, 80 req/s | 18.8 ms | 286 ms |
  | laya-multilingual | bursty, 84 req/s | 31.6 ms | 2076 ms |
  | laya-typed-decisions | Poisson, 33 req/s | 28.8 ms | 329 ms |

  Medium, long and 4-question classes run on the GPU under both configurations. They see
  equal or lower latency with `auto`, because the GPU queue no longer holds the short
  requests.
- **Why multilingual misses the stricter throughput baseline.** Two MLX streams in
  separate processes overlap on the GPU (92.3 req/s). The product runs one MLX queue
  (55.8 req/s). A second MLX worker is a candidate optimisation (§13), not part of v0.2.

## Findings recorded for the roadmap

1. **Request-driven host slowdown.** With both devices busy, a device thread woken over
   IPC runs its host code 4–6× slower.
2. **Core ML's Python `predict` holds the GIL for much of an ANE call.** A Python loop in
   another thread ran at 42% of its normal rate.
3. **Consequence for placement.** Neither ANE placement dominates:
   - thread wins for the ModernBERT-large models (about 10 ms per ANE request);
   - process wins for mmBERT-base (about 4 ms per request, about 250 requests/s, where
     the GIL cost dominates).
4. **Throughput mechanics.**
   - A single MLX FIFO queue gives less GPU throughput than two concurrent MLX streams.
   - Short requests queued behind long ones on the GPU are what the ANE path removes.
