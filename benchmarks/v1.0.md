# laya-apple v1.0 benchmark report

## Scope

The comprehensive v1.0 suite: correctness against upstream, single-request and
end-to-end latency, auto device routing, heterogeneous GPU+ANE serving under closed
and open load, option-order robustness, and a reproducibility check against the v0.1
and v0.2 release figures. Every headline claim in this report uses only v1.0 data
(`benchmarks/v1.0/`), not the historical Phase -1 or v0.1/v0.2 numbers, except where a
number is explicitly marked as historical for context.

All measurements are on Apple M4 Max, macOS 26.6.2 (25G83), MLX 0.32.2, coremltools
9.0, Python 3.12.14 — verified in the `platform` fields of `benchmarks/v1.0/raw.jsonl`,
`comparators-latency.jsonl` and `probe.json`.

## Correctness vs upstream PyTorch FP32

`scripts/v1_report.py parity`, against unmodified upstream Laya on PyTorch CPU FP32 —
the golden rows shipped in `laya_apple/parity/goldens`.

**Definitions** (`research/phase-0-feasibility/methodology.md` §5,
`laya_apple/parity/__init__.py`):
- **Probability error**: max \|Δ\| of calibrated probability vs. the reference, over
  the question's options.
- **Hard mismatch**: the argmax decision differs from the reference **and** the
  reference's own top-1/top-2 calibrated margin is ≥ 2× the tolerance for that
  precision (0.04 for FP16, 2e-4 for FP32). This is a real defect.
- **Near-tie flip**: the decision differs, but inside that margin band — a
  perturbation within tolerance can legitimately flip the argmax there. These are
  listed row by row, never hidden, and never counted as failures.
- **FP16 gate**: probability error ≤ 0.02, action probability error ≤ 0.02, 0 hard
  mismatches, all outputs finite, repeated identical calls bitwise identical.
- **FP32 gate**: the same, at ≤ 1e-4.

## Auto routing

Measured behaviour of `device="auto"` from the data above, plus the derivation rule
behind it (`docs/support-matrix.md`, "How the auto-ANE buckets were derived"):
`laya_apple/data/routing.json` walks each model's ANE buckets in increasing order — a
bucket joins auto routing only if it passed BC1S parity **and** the ANE forward P50 at
that bucket beats the MLX forward P50 at the *previous* bucket (for the first bucket,
MLX at that same length). The walk stops at the first bucket that fails. Multi-question
requests never auto-route to the ANE: MLX batching wins at every measured length for 4
and 8 questions.

**Measured crossover ≠ production routing threshold.** For `laya-multilingual` at
L256, the ANE forward P50 (8.30-8.34 ms) is still slightly *faster* than MLX GPU at the
same length (8.58 ms) — a real, measured crossover in laya-apple's favor. But L256 is
not in the auto-ANE bucket set for this model (routing tops out at L128): the
derivation rule compares the L256 ANE figure against MLX at the *previous* bucket,
L128 (6.43-6.46 ms), which the ANE figure does not beat. The routing table is
deliberately conservative relative to a naive head-to-head comparison at the same
length.

**Multi-question requests go to MLX.** For `laya-multilingual` at L128 with 4
questions, only the MLX figure was measured in v1.0 (13.79-13.86 ms, `raw.jsonl`); no
v1.0 ANE q4 run exists, since q4 never auto-routes to the ANE. For context only, the
historical Phase -1 figure for the same configuration (Core ML BC1S ANE-graph,
`CPU_AND_NE`, q4, L128) was 17.01 ms
(`research/phase-0-feasibility/reports/latency.md`) — slower than MLX even then, which
is consistent with the routing rule's decision to never send multi-question requests
to the ANE.

## Heterogeneous GPU + ANE serving, closed loop

`scripts/v1_report.py hetero`, from `scripts/bench_concurrency.py --part a`.

| Model | GPU-only req/s | GPU + ANE req/s | Multiplier | Short P99 ms (GPU-only → GPU + ANE) | Long req/s (GPU-only → GPU + ANE) | Answer mismatches |
|---|---:|---:|---:|---:|---:|---:|
| laya | 41.9 | 122.5 | 2.92× | 48.1 → 11.2 | 20.9 → 24.6 | 0 |
| laya-multilingual | 55.7 | 241.8 | 4.34× | 36.5 → 6.9 | 27.9 → 31.7 | 0 |
| laya-typed-decisions | 24.0 | 109.6 | 4.57× | 84.3 → 11.9 | 12.0 → 12.6 | 0 |

**Methodology:** one Laya instance per configuration, `execution="workers"`. GPU-only
baseline: `device="gpu"`, `execution="workers"` — both streams (short, long) on one MLX
worker queue. Heterogeneous: `device="auto"`, `execution="workers"`, ANE placement per
model from `laya_apple/data/placement.json` (`laya`: thread, `laya-typed-decisions`:
thread, `laya-multilingual`: process — the placement with the lower short-stream P99,
per model). Short/long request lengths per model, taken from the recorded run args:
`laya` short=128/long=512, `laya-multilingual` short=96/long=1024,
`laya-typed-decisions` short=128/long=1024. One closed-loop client thread per stream.
20 s measurement windows, 3 cycles run in alternating order (GPU-only, heterogeneous,
GPU-only, …), median over cycles. 5 warm-up predictions per request type per instance
before each window. Every answer is compared with the inline answer computed on the
same device that served it.

**Why it helps:** short requests are ANE-eligible and finish in single-digit
milliseconds without touching the GPU queue; long requests continue to run on the GPU.
Splitting the two removes head-of-line blocking (a long GPU forward pass no longer
makes every short request behind it wait), and both engines are kept busy
simultaneously instead of one queue serializing everything.

## Multilingual reproducibility note

The v0.2 release recorded a `laya-multilingual` heterogeneous aggregate throughput of
198.3 req/s. `scripts/compare_bench.py concurrency benchmarks/v0.2 benchmarks/v1.0`
shows the v1.0 re-run at 241.8 req/s (+21.9%) — the only figure in the full
reproducibility comparison (see below) outside ±2%.

A same-machine, back-to-back A/B isolates the cause (`benchmarks/v1.0/ab/`,
`scripts/bench_concurrency.py --part a` run twice, once on the tagged v0.2.0 code and
once on v1.0 code, no other change):

| Condition | v0.2.0 code | v1.0 code | Δ |
|---|---:|---:|---:|
| solo, short stream only (req/s) | 243.7 | 242.0 | -0.7% |
| GPU-only baseline (req/s) | 55.7 | 55.7 | +0.0% |
| heterogeneous (req/s) | 249.0 | 238.8 | -4.1% |

Solo and GPU-only-baseline throughput reproduce within 1% on both codebases. The
heterogeneous figure itself varies run to run on both codebases (198.5-260.8 req/s
across the three A/B cycles) more than solo or GPU-only do — this is expected
closed-loop concurrency variance, not a regression between code versions. The original
v0.2 recorded figure of 198.3 req/s was on the low end of that same variance band
because of machine state at the time it was recorded, not because of a code
difference: the A/B run of the *old* v0.2.0 code on today's quiet machine reproduces at
249.0 req/s, close to the v1.0 code's 238.8 req/s, not close to the originally recorded
198.3 req/s.

## Option-order robustness

`choice` questions can be sensitive to the order of the `criteria` dict — measured in
`research/option-order/`. Summary: this is a property of the upstream Laya model, not a
laya-apple defect. Unmodified upstream PyTorch changes its decision under permutation
on 22.5% (`laya`) / 35.0% (`laya-typed-decisions`) of a 40-case set; laya-apple's MLX
FP32 backend reproduces upstream's decision for every permutation exactly (0
per-permutation mismatches, both models). FP16 (GPU and ANE) has a small number of
extra per-permutation mismatches, all inside the near-tie band, so
`defects_outside_near_tie_band` is empty for every runner. Full numbers and
methodology: `research/option-order/README.md`.

Raw files: `benchmarks/v1.0/raw.jsonl` (laya-apple latency), `comparators-latency.jsonl`
and `parity/` (comparators), `placement-*.json` (closed-loop mix), `concurrency-*.json`
(open-loop mix), `option-order-*.json` (option-order runs), `ab/` (the v0.2.0-vs-v1.0
A/B), `demo-heterogeneous-routing.txt` and `probe.json`.

## Reproducibility: single-request latency against v0.1

`scripts/release_bench.py benchmarks/v1.0/raw.jsonl`:
- the same 50 configurations as v0.1 (model × device × exact length × question count);
- a fresh process per configuration, two passes with the second in reverse order;
- 10 warm-up and 50 timed iterations;
- P50 is the mean over the two passes.

The baseline is `benchmarks/v0.1/raw.jsonl`.

**Result: every figure reproduced within ±1.8%.** That is 50 configurations × 2
boundaries (forward and end-to-end predict). No change exceeded 2%.
