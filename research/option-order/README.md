# Option-order robustness check

Does permuting the `criteria` list of a `choice` question change the model's decision?
Nothing in the task schema gives criteria order meaning: `laya_apple.prompt.render_options`
turns a choice question's `criteria` dict into an ordered list of masked markers
(`build_sequence`), and the label a marker stands for is purely a matter of dict order. A
well-behaved classifier's chosen label (by semantic label, not position) and per-label
probabilities should not depend on that order.

This check measures that property for laya-apple, and separately for unmodified upstream
Laya, over the same deterministic case set — so any instability found can be attributed
correctly: a **documented model property** if upstream itself is unstable on that case, or a
**laya-apple runtime defect** if laya-apple diverges from upstream's per-permutation decisions
outside the near-tie band defined by the Phase -1 parity methodology
(`research/phase-0-feasibility/methodology.md` §5).

## Case set

`cases.json` (generated by `scripts/option_order.py write-cases`, deterministic, stdlib
only — no model load) has 40 `choice` questions: 8 instruction templates with 3-5 options
each, over 5 short generic contexts (all text written for this project). For each case:

- options ≤ 4: every permutation of the criteria order (6 or 24 permutations).
- options = 5: a fixed-seed sample of 6 permutations (the identity order plus 5 sampled
  from the remaining 119), not the full 120.

Regenerate with:

```
uv run python scripts/option_order.py write-cases
```

## Running laya-apple

```
uv run python scripts/option_order.py run --device gpu --dtype float32 \
    --model laya-typed-decisions --model laya \
    --output benchmarks/v1.0/option-order-gpu-float32.json

uv run python scripts/option_order.py run --device gpu --dtype float16 \
    --output benchmarks/v1.0/option-order-gpu-float16.json

uv run python scripts/option_order.py run --device ane --dtype float16 \
    --output benchmarks/v1.0/option-order-ane-float16.json
```

`--device ane` only serves the single-question requests this case set already uses within
the model's validated auto-ANE buckets; a case whose prompt falls outside a validated bucket
is recorded per-permutation as an `error` entry rather than aborting the run.

For each case, the output records the chosen label and per-label probability for every
permutation, `decision_changed` (whether the chosen label ever differed across
permutations) and `max_abs_delta_prob` (the largest per-label probability swing across
permutations).

## Running the upstream reference

Upstream Laya (PyTorch, CPU, FP32) needs the research venv, which has the pinned upstream
`laya` package and torch:

```
cd research/phase-0-feasibility
uv run python ../option-order/upstream.py --model laya-typed-decisions \
    --output ../../benchmarks/v1.0/option-order-upstream-laya-typed-decisions.json
uv run python ../option-order/upstream.py --model laya \
    --output ../../benchmarks/v1.0/option-order-upstream-laya.json
```

It runs the exact same `cases.json` and criteria permutations, and writes the same output
schema as `scripts/option_order.py run` (one model per file, no `--device`/`--dtype`: it is
always CPU FP32).

## Comparing

```
uv run python scripts/option_order.py compare \
    benchmarks/v1.0/option-order-gpu-float32.json \
    benchmarks/v1.0/option-order-upstream-laya-typed-decisions.json
```

This reports, per model common to both files: the fraction of cases whose decision changes
under permutation in each run, how many cases both runs are unstable on, and every
per-permutation decision mismatch between the two runs. A mismatch is separated into the
near-tie band (upstream's own top-1/top-2 calibrated-probability margin on that permutation
is below `2 × tolerance`, where a perturbation within tolerance can legitimately flip the
argmax per the parity methodology) versus `defects_outside_near_tie_band` — mismatches with
no such excuse, which are runtime bugs, not model properties.

## Interpreting the results

- If laya-apple GPU FP32's `decision_changed_fraction_a` tracks upstream's
  `decision_changed_fraction_b` and `defects_outside_near_tie_band` is empty, any observed
  option-order sensitivity is a property of the upstream Laya model itself, not a laya-apple
  runtime defect.
- Any non-empty `defects_outside_near_tie_band` is a laya-apple runtime defect: GPU FP32 must
  reproduce upstream's per-permutation decisions exactly outside the near-tie band.
- FP16 (`gpu float16`) and the ANE additionally carry their own quantization-level
  instability; compare them against the GPU FP32 laya-apple run (not only upstream) to see
  how much of their extra sensitivity, if any, is precision-related rather than a defect.

For actual numbers: see `benchmarks/v1.0/option-order-*.json`. The section below records
the v1.0 run's result once, as a conclusion, not as a live table — re-run `compare` for the
current numbers.

## Results (v1.0)

`scripts/option_order.py compare` of each laya-apple runner against the matching upstream
file, tolerance 1e-4 (FP32) / 0.02 (FP16):

| Runner | Model | Cases | Decision-changed, laya-apple | Decision-changed, upstream | Per-permutation mismatches | Defects outside near-tie band |
|---|---|---:|---:|---:|---:|---:|
| GPU FP32 | laya | 40 | 22.5% | 22.5% | 0 | 0 |
| GPU FP32 | laya-typed-decisions | 40 | 35.0% | 35.0% | 0 | 0 |
| GPU FP16 | laya | 40 | 22.5% | 22.5% | 0 | 0 |
| GPU FP16 | laya-typed-decisions | 40 | 37.5% | 35.0% | 3 | 0 |
| ANE FP16 | laya | 40 | 22.5% | 22.5% | 1 | 0 |
| ANE FP16 | laya-typed-decisions | 40 | 35.0% | 35.0% | 4 | 0 |

**Conclusion.** Sensitivity to option order is a property of the upstream Laya model, not
of laya-apple: unmodified upstream (PyTorch CPU FP32) changes its decision under
permutation on 22.5% (`laya`) and 35.0% (`laya-typed-decisions`) of the case set — the same
fraction laya-apple GPU FP32 shows, with 0 per-permutation mismatches against upstream. The
laya-apple MLX FP32 backend reproduces upstream's decision for every permutation, on every
case, exactly. FP16 (GPU and ANE) has a handful of extra per-permutation mismatches (1-4 out
of 40 cases × up to 24 permutations), all of which fall inside the near-tie band — upstream's
own top-1/top-2 calibrated margin on that permutation is below `2 × tolerance` — so none of
them counts as a defect. `defects_outside_near_tie_band` is empty for every runner.
