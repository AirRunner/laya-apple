# laya-apple 1.0.0

## What is laya-apple?

A correctness-validated Apple silicon runtime for
[Laya](https://github.com/NandhaKishorM/laya). Laya models take a context and a set of
typed questions (`choice`, `score`, `noul`) and return calibrated decisions in one forward
pass.

laya-apple:
- runs every Laya workload on the **MLX GPU**;
- adds the **Apple Neural Engine** only for configurations proven, on the machine that
  uses them, to give the same decisions as upstream Laya;
- routes each request to one engine and serves both engines **at the same time**.

1.0.0 declares the public API, CLI, routing reasons and artifact manifest stable
([`docs/api.md`](https://github.com/tc3oliver/laya-apple/blob/main/docs/api.md)).
There are no breaking changes since 0.3.0.

## Why another Apple Laya runtime?

Laya already runs on Apple silicon through a GPU path and through Core ML. laya-apple
builds on that work ([`NOTICE`](https://github.com/tc3oliver/laya-apple/blob/main/NOTICE))
and adds three things:
- a parity gate against upstream PyTorch FP32 for every ANE configuration, on the
  machine that uses it;
- automatic, measured routing between the GPU and the ANE per request;
- concurrent GPU + ANE serving from one `Laya` instance.

## Correctness finding

On Apple M4 Max, macOS 26.6.2, coremltools 9.0, the ordinary Core ML export of Laya
runs without error and is fast on `CPU_AND_NE`, but it changes decisions against upstream
PyTorch FP32:

| Model | Ordinary export · `CPU_AND_NE` | laya-apple ANE FP16 |
|---|---|---|
| laya | 12 hard mismatches, max prob error 0.56 | 0 hard, 1 near-tie flip, 0.0122 |
| laya-multilingual | 85 hard mismatches, max prob error 1 | 0 hard, 0 near-tie flips, 0.0128 |
| laya-typed-decisions | 19 hard mismatches, max prob error 0.418 | 0 hard, 0 near-tie flips, 0.00767 |

At laya-typed-decisions L1024 the ANE compiler fails and Core ML runs the same export on
the CPU without raising (2201.8 ms per forward pass). laya-apple uses a channel-first
(BC1S) graph instead, and registers an ANE artifact only after it passes parity and shows
a 100% Neural Engine compute plan. Details:
[`docs/correctness.md`](https://github.com/tc3oliver/laya-apple/blob/main/docs/correctness.md).

## Automatic routing

`device="auto"` sends short single-question requests to the ANE and long or
multi-question requests to MLX, using per-bucket thresholds derived from measurements.
Every result records the reason in `result.runtime.routing_reason`. On a machine with no
validated profile, `auto` uses MLX only until `laya-apple calibrate` builds one.

## Heterogeneous GPU + ANE serving

```python
with Laya.from_pretrained("convaiinnovations/laya-typed-decisions", execution="workers") as model:
    futures = [model.submit(context=c, questions=q) for c, q in requests]
```

The GPU runs in a worker process and the ANE on a thread or in a process, per model. Each
request runs on one device. Short requests stop waiting behind long ones.

## Key benchmark

Mixed short/long closed-loop workload, one `Laya` instance, Apple M4 Max, macOS 26.6.2:

| Model (short / long tokens) | GPU-only req/s | GPU + ANE req/s | Throughput | Short-stream P99, ms | Answer mismatches |
|---|---:|---:|---:|---:|---:|
| laya (128 / 512) | 41.9 | 122.5 | **2.92×** | 48.1 → 11.2 | 0 |
| laya-multilingual (96 / 1024) | 55.7 | 241.8 | **4.34×** | 36.5 → 6.9 | 0 |
| laya-typed-decisions (128 / 1024) | 24.0 | 109.6 | **4.57×** | 84.3 → 11.9 | 0 |

Open-loop arrivals, forward latency, end-to-end latency and option-order results are in
[`benchmarks/v1.0.md`](https://github.com/tc3oliver/laya-apple/blob/main/benchmarks/v1.0.md).

## How to reproduce

```bash
git clone https://github.com/tc3oliver/laya-apple && cd laya-apple
uv sync
uv run python scripts/v1_report.py all      # renders every v1.0 table from benchmarks/v1.0/
```

Re-measuring needs the `ane` and `convert` extras and locally built ANE artifacts. The raw
data, the command behind each number, the recorded environment and the full re-run
order are in
[`docs/reproducibility.md`](https://github.com/tc3oliver/laya-apple/blob/main/docs/reproducibility.md).

## Known limitations

- Every benchmark comes from one Apple M4 Max on macOS 26.6.2.
- Routing thresholds are not portable. On another SoC, `auto` stays on MLX until the ANE
  artifacts are built and calibrated there.
- The ANE path is fixed-shape and batch 1. Long contexts stay on MLX.
- Isolation between the two engines is partial; with the ANE on a thread, heavy Python
  work in the calling thread slows it.
- The first Core ML compile on a fresh artifact location takes minutes per model.
  `ane_startup="background"` serves on MLX meanwhile.
- `choice` decisions can depend on option order. This is a property of upstream Laya,
  which laya-apple MLX FP32 reproduces exactly.
- Energy use, quantized artifacts and other SoCs are not yet measured.
