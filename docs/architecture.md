# Architecture

laya-apple runs Laya on two Apple silicon engines: the GPU through MLX, and the Neural
Engine (ANE) through Core ML. It decides per request which engine runs it, and under
`execution="workers"` it keeps both engines busy at the same time.

```
                     Laya API  (laya_apple.Laya)
                        │
                        ▼
                 Capability Registry   (registry + routing.json + verified artifacts + platform profile)
                        │
                        ▼
                     Router            (routing.decide / scheduling.decide_queued)
                  /          \
          MLX / Metal      Core ML
              GPU             ANE
                  \          /
             concurrent serving        (execution="workers")
```

## Layers

| Layer | Module | What it does |
|---|---|---|
| API | `laya_apple/model.py` | `Laya.from_pretrained`, `predict`, `submit`, `apredict`. Builds prompts, asks the router for a device, formats `Result` and `RuntimeInfo`. |
| Capability registry | `laya_apple/registry.py`, `laya_apple/data/routing.json` | Pinned checkpoints (revision + weight hash), offered ANE buckets, auto-routing buckets and service-time estimates. `routing.json` is generated by `scripts/derive_routing.py` from committed measurements, not written by hand. |
| Verified artifacts | `laya_apple/artifacts.py`, `laya_apple/lifecycle.py` | Manifest, file hash, compute-plan and parity checks for each Core ML artifact; build locking, quarantine, prune, warm, export/import. |
| Platform profile | `laya_apple/profiles.py` | Matches this machine (SoC, macOS major, coremltools) to a validated profile, or to a local profile written by `laya-apple calibrate`. |
| Router | `laya_apple/routing.py`, `laya_apple/scheduling.py` | `decide` (inline) and `decide_queued` (workers). |
| Backends | `laya_apple/backends/mlx.py`, `laya_apple/backends/coreml_ane.py` | Prompt rows in, decision and action logits out. Prompt construction and calibration are shared, so both return the same schema. |
| Executor | `laya_apple/executor.py` | One FIFO queue per device; worker processes and the ANE thread. |

## MLX is the general backend

`backends/mlx.py` runs every model, length, question count and batch, in FP16 or FP32.
Every request has a GPU path. A request only goes to the ANE when the conditions below
hold; otherwise it runs on MLX.

## The ANE is a validated specialized accelerator

`backends/coreml_ane.py` runs fixed-shape, batch-1, FP16 artifacts on `CPU_AND_NE`, one
artifact per length bucket. A row is padded up to the smallest offered bucket that holds
it. It is never truncated, and a row longer than every bucket raises
`UnsupportedShapeError`.

An artifact is loaded only through `artifacts.load_verified`, which checks:
- the manifest schema, model revision, weight hash, graph, bucket and compute units;
- the build platform profile against this machine;
- the file hash;
- the Core ML compute plan: 100% of operations on the Neural Engine, 0 device
  transitions (`check_ane_placement`);
- the parity record written when the artifact was built on this machine.

## Correctness-aware routing

The router decides before the request runs, and records why in
`RuntimeInfo.routing_reason`. Under `device="auto"` a request goes to the ANE only if:
- the machine matches a validated or locally calibrated platform profile;
- the request has one question;
- its length fits an auto bucket from `routing.json`, and that bucket's artifact loaded
  and verified on this machine, including its parity record.

A bucket joins `auto` only if its artifact passed parity and its ANE time beats MLX at
the previous, shorter bucket (`docs/support-matrix.md`). `routing.decide` is a pure
function of the request shape and what loaded. `scheduling.decide_queued` adds one
input, a snapshot of each device's backlog. With both queues empty it returns exactly
what `decide` returns.

## Request-level heterogeneous execution

One request runs on one device. The GPU and the ANE serve different requests at the
same time; a single request is never split across them.

With `execution="workers"` (`executor.py`):
- the GPU runs in a worker process;
- the ANE runs on a dispatcher thread in the caller's process, or in a worker process,
  per model from `laya_apple/data/placement.json` (generated by
  `scripts/derive_placement.py` from measurements);
- each device has one FIFO queue and runs one job at a time.

With `execution="inline"` (the default), both backends live in the calling process and
requests run one at a time per instance.

## Unsupported ANE paths fail

- `device="ane"` runs the validated artifact on `CPU_AND_NE` in FP16, or raises:
  `UnsupportedShapeError`, `ArtifactMissingError` or `ComputeUnitMismatchError`.
- Under `device="auto"`, a bucket whose artifact fails verification is not offered, and
  the request goes to MLX with a reason such as `ane_artifact_unavailable`. That
  decision is made before the request runs.
- A request that fails on a device is not re-run on the other device.

Every path and its test are listed in [`no-silent-fallback.md`](no-silent-fallback.md).

## Runtime placement probe

A compute plan is static; it cannot show where the *loaded* model runs. So every loaded
bucket also passes `probe_placement` (`backends/coreml_ane.py`): it times the loaded
model against a `CPU_ONLY` instance of the same artifact on the same input, back to
back. If the ratio exceeds `PROBE_MAX_RATIO` (0.8), the load raises
`ComputeUnitMismatchError`. The evidence for that threshold is
`benchmarks/v1.0/probe.json`, produced by `scripts/bench_probe.py`.
